## 1 Summary

本项目将在现有 AI-Range-Demo 的产品资产基础上，新建一个面向三类用户的 AI 原生攻防数据生产平台 Demo。新版本不再以“测试、训练、数据中心”等功能模块组织产品，而是分别围绕训练用户、监管用户、开发者与企业用户的核心任务，提供三套清晰入口，并共享场景、任务、运行轨迹、证据、数据版本和治理底座。

平台的长期目标是形成自动闭环：用户只需给出需要训练、测试或生产数据的场景需求，系统即可在受控边界内生成场景规格、组合靶场环境和测试 Agent、自主执行攻防、验证结果、精炼数据并沉淀知识。第一版仍是可交互 Demo，不直接连接真实生产网络，也不提供无约束攻击能力。

## 3 Background

### 3.1 当前 Demo 基线

代码语法检查通过，主要页面可正常运行。现有资产中最值得保留的是：

1. 测试任务创建、运行观察、结果确认和报告闸门的完整演示逻辑。
2. 五套靶场环境卡片、环境详情和拓扑表达。
3. 外部模型与 Agent 接入、校验状态和调用统计的产品概念。
4. 轨迹、风险、题库、报告和模型版本等样例数据。
5. 深浅主题、基础视觉 Token 和较完整的浏览器测试场景。

### 3.2 当前 Demo 与新规划的差距

| 维度 | 当前 Demo | 新规划要求 | 结论 |
|---|---|---|---|
| 用户组织 | 按态势感知、测试任务、训练任务、数据中心、网关组织 | 严格按训练、监管、开发者与企业三类用户组织 | 需要重做信息架构 |
| 训练用户 | 主要创建和监控 RL、CPT、SFT、DPO 训练任务 | 研究员主要消费现有数据集，重视隐私和效果回传 | 现有训练模块方向不匹配 |
| 监管用户 | 测试任务与结果确认已有雏形 | 需要冻结条件、批量运行、横向比较、审计报告 | 可复用流程，需补标准化能力 |
| 企业用户 | 靶场任务和接入网关分散存在 | 需要用编排任务规模化 Roll 结构化轨迹 | 需要重组为数据生产工作台 |
| 数据价值 | 数据中心展示数量和导出 | 需要授权、质量、版本、消费和效果闭环 | 需要重构数据引擎 |
| AI 原生 | 主要是预置数据和定时动画 | 需要需求理解、场景生成、环境与 Agent 生成、自主验证 | 需要新增核心产品主线 |
| 工程形态 | 浏览器本地状态，无真实服务接口 | 新 Demo 需要清晰领域模型和可替换服务层 | 不应继续扩展单体 `app.js` |
| 文档一致性 | README 和代码注释仍标注 V3.5，主分支已到 V3.9.2 | 文档、版本和验收应同步 | 新仓库需建立单一版本来源 |

### 3.3 为什么新建仓库

不建议继续在旧仓库中叠加功能。旧仓库适合保留为 830 演示档案，但其单文件结构、历史页面和静态数据会让新用户架构被旧模块牵制。新仓库应选择性迁移视觉 Token、场景素材、任务运行表达、结果确认和测试资产，不复制旧的单体结构和所有页面。

## 4 Objective

### 4.1 产品目标

建立一个以可信结构化轨迹为核心产物的 AI 攻防演练平台。平台同时满足三个目标：

1. 让实验室研究员安全消费已有数据，并验证数据是否真正提升模型或 Agent。
2. 让监管评测人员在冻结条件下运行模型或 Agent 测试，形成可比较、可复现、可审计的结论。
3. 让开发者与企业通过平台编排好的任务低门槛 Roll 轨迹，获得可交付的结构化数据。

### 4.2 北极星指标

**有效轨迹数据量**：经授权、通过质量门禁、被训练或评测实际消费，并完成结果或效果回传的轨迹单元数量。

任务数、模型调用量、原始日志量和生成文本量只作为过程指标，不能单独证明产品价值。

### 4.3 Key Results

以下数值是 PRD 建议值，需在开发前确认。

#### 2026 年 9 月 30 日

- KR1：三类用户均能独立完成一条端到端最小流程，核心步骤完成率达到 90% 以上。
- KR2：正式轨迹必填字段完整率达到 95% 以上，关键结果与证据关联率达到 100%。
- KR3：同一 Run 可追溯到项目、场景、环境、Agent、步骤、证据、授权和数据版本。
- KR4：跨角色越权、未授权导出和未授权数据回流为 0。
- KR5：至少完成一个数据版本的消费登记和效果回填样例。

#### 2026 年 12 月 30 日

- KR1：批准场景范围内的正常任务无人值守完成率达到 80% 以上。
- KR2：监管批量评测的固定条件复现率达到 90% 以上，评分一致性达到项目确认门槛。
- KR3：正式数据版本的结构化完整率达到 98% 以上，证据完整率达到 95% 以上。
- KR4：至少一个模型或 Agent 使用平台数据后，在固定基准上产生可量化提升，且安全指标不恶化。
- KR5：至少一个开发者或企业数据生产项目证明交付周期或单位有效轨迹成本有明确改善。
- KR6：知识库中的失败模式或场景配方至少成功驱动一轮新场景生成和验证。

## 5 Market Segments

### 5.1 训练用户

- **主要用户**：实验室内部安全研究员、模型研究员和 Agent 研究员。
- **核心任务**：寻找与能力短板匹配的数据，在隐私和用途约束下消费数据，并验证训练或策略调整后的效果。
- **当前痛点**：数据来源和质量不清；数据版本难追溯；敏感数据不能直接下载；训练结果无法反馈到数据选择和场景生产。
- **产品边界**：平台负责数据发现、授权、受控消费、版本和效果回传，不建设通用训练调度与算力管理平台。

### 5.2 监管用户

- **主要用户**：负责模型或智能体安全测试、验收和审计的评测人员。
- **核心任务**：在统一任务、环境、工具和评分规则下运行测试，比较多个对象并签发可信报告。
- **当前痛点**：测试条件容易变化；结果难复现；总分缺少证据；人工汇总报告成本高。
- **产品边界**：平台提供测试执行和证据链，不代替监管标准制定和最终责任签署。

### 5.3 开发者与企业用户

- **主要用户**：需要安全轨迹数据的开发团队、Agent 团队以及需要验证自有环境或 Agent 的企业客户。
- **核心任务**：选择平台编排的靶场任务，接入自有 Agent 或环境，批量运行并获得结构化轨迹和项目报告。
- **当前痛点**：安全场景搭建成本高；轨迹格式不统一；失败数据难复现；数据归属和用途不清。
- **产品边界**：所有执行必须位于批准的隔离环境；不提供对真实互联网和未授权资产的攻击能力。

## 6 Value Propositions

| 用户 | 获得的价值 | 避免的损失 | 平台差异化 |
|---|---|---|---|
| 训练用户 | 更快找到可用数据，安全完成消费，并看到真实增益 | 误用敏感数据、重复清洗、训练后无法归因 | 把安全场景、轨迹证据、数据版本和效果回传连接起来 |
| 监管用户 | 用冻结条件批量测试多个模型或 Agent，直接获得证据化报告 | 环境变化导致不可比、评分争议、手工审计成本 | 环境、对象、评分、证据和报告采用同一版本链 |
| 开发者与企业用户 | 复用任务配方和靶场组件，规模化产生专属结构化数据 | 从零搭建环境、低质量日志、交付周期不可控 | 将任务执行、自动验证、数据精炼和项目授权组合成一条链路 |
| 平台运营方 | 形成数据被消费、效果被验证、知识反哺场景的飞轮 | 只累计任务和日志但无法证明业务价值 | 以有效数据和实际增益作为北极星，而非调用量 |

### 7.2 三条关键用户流程

#### 训练数据消费

能力短板 → 筛选授权数据 → 查看数据卡 → 创建受控消费记录 → 关联模型版本 → 回填固定基准结果 → 将允许回流的失败类型转为新场景需求。

#### 监管测试

创建评测项目 → 选择标准任务集 → 冻结环境、Agent、工具和评分规则 → 加入待测对象 → 批量执行 → 自动初审 → 人工处理争议项 → 签发带证据的审计报告。

#### 开发者与企业数据生产

定义目标数据 → 选择任务配方 → 接入或选择 Agent 和环境 → 确认并发、预算、安全边界和停止条件 → 自动 Roll → 自动验证和精炼 → 生成数据版本、数据卡和复现包 → 受控交付。

### 7.3 AI 原生闭环

| AI 单元 | 输入 | 动作 | 输出 | 安全约束 |
|---|---|---|---|---|
| 需求理解器 | 训练短板、评测要求、企业场景、历史失败 | 提取目标、成功条件、数据需求和边界 | DataGoal | 低置信度字段必须明确标记 |
| 场景编译器 | DataGoal、知识库、批准组件 | 生成场景规格、难度、攻击面和数据字段 | SceneSpec | 仅使用批准的漏洞和组件范围 |
| 环境工厂 | SceneSpec、镜像、网络策略、环境适配器 | 组合拓扑、服务、状态、漏洞和快照 | EnvironmentVersion | 禁止访问未授权真实资产 |
| Agent 工厂 | 目标、角色模板、工具目录 | 配置攻击、防守、裁判和扰动 Agent | AgentVersion | 工具白名单、最小权限和预算 |
| 自主编排器 | 冻结任务包、并发和停止条件 | 启动、调度、恢复、重试和成本控制 | Run 批次 | 越权、逃逸和预算异常立即阻断 |
| 自动验证器 | 轨迹、规则、证据和重放环境 | 规则检查、异构裁判、重放和证据校验 | 验证结果 | 裁判模型不能作为唯一真值 |
| 数据精炼器 | 已验证 Run | 结构化、去重、脱敏、标注、评分和版本化 | DatasetVersion | 保留来源和全部变换记录 |
| 知识沉淀器 | 失败模式、质量问题和消费效果 | 抽象场景配方、策略、基线和失效条件 | KnowledgeItem | 跨项目复用前必须去敏 |

### 7.4 无人值守边界

正常路径可以自动完成，但以下情况必须停止或进入人工处理：

- 新漏洞类别、新外部网络、未审批工具或高风险动作。
- 数据越权、环境逃逸、敏感信息泄露和异常成本。
- 证据冲突、评分不一致、重放失败或裁判分歧。
- 企业数据跨项目复用，或监管数据转为训练用途。
- 自动生成环境未通过隔离、重置、复现和保真度检查。

### 7.5 核心数据对象

第一版只定义最少且稳定的领域对象：

- `UserRole`、`Project`、`Policy`
- `DataGoal`、`SceneSpec`、`TaskTemplate`
- `EnvironmentVersion`、`AgentVersion`、`ToolVersion`
- `Run`、`StepTrace`、`StateSnapshot`
- `Evidence`、`ValidationResult`、`QualityScore`
- `DatasetVersion`、`DataCard`、`EvaluationReport`
- `ConsumptionRecord`、`EffectReport`
- `KnowledgeItem`、`ScenarioRecipe`

不为尚未验证的商业模式、市场交易和复杂审批创建抽象。

### 7.6 数据与隐私要求

1. 不采集或要求模型输出隐藏思维链。仅记录可观察输入、动作、工具调用、环境反馈、结果、证据和事后摘要。
2. 数据对象必须携带所有者、许可证、允许用途、隐私级别、保留期和导出策略。
3. 训练、监管和企业项目默认隔离；跨项目和跨用途流转必须重新授权。
4. 企业原始敏感数据优先采用受控计算或挂载，不默认允许下载。
5. 自动脱敏不是唯一保障；高风险数据发布前仍需策略校验和抽检。
6. 所有正式数据版本必须保留来源、处理步骤、验证结果和消费记录。

### 7.7 930 功能范围

#### P0 必须完成

- 三类角色入口和项目隔离。
- 三条端到端薄链路。
- 统一 Run、Trace、Evidence、DatasetVersion 数据规范。
- 一个真实靶场任务和一个真实或可验证的 Agent 接入。
- 资源版本冻结、任务状态、事件流、暂停、终止和重试。
- 轨迹必填字段、证据关联、去重、敏感扫描和授权门禁。
- 数据卡、消费记录、评测报告和企业数据交付摘要。
- 三组验收账号、真实演示脚本和异常预案。

#### 930 明确不做

- 从任意自然语言生成完整高保真靶场。
- 通用训练调度、算力运营和完整 MLOps。
- 无边界互联网攻击和真实资产扫描。
- 复杂开发者门户、交易市场、计费和大规模开放运营。
- 自动把企业或监管数据转入训练用途。

### 7.8 1230 增量范围

- 能力短板到数据推荐、私有消费和效果回传。
- 标准任务集、多模型或 Agent 批量评测、横向比较和审计报告。
- 并发 Roll、任务配方复用、自有 Agent 或环境适配、项目级数据交付。
- 场景编译器和基于批准组件的环境生成。
- 攻击、防守、裁判和扰动 Agent 配置生成。
- 无人值守任务调度、自动恢复、预算和停止条件。
- 重放、规则、异构裁判和证据充分性组合验证。
- 自动精炼、质量评分、数据配方、消费和效果闭环。
- 失败模式和场景配方沉淀，并驱动下一轮场景生成。

### 7.9 新仓库工程方案

#### 仓库策略

- 新建独立仓库，不从旧仓库直接 Fork，也不复制全部历史页面。
- 旧仓库保持只读，作为 830 Demo 和交互资产参考。
- 仅迁移主题 Token、必要场景素材、任务运行表达、结果确认逻辑和可复用测试用例。
- 新仓库 README、PRD、版本号和 Demo 页面使用同一产品版本。

#### 推荐技术栈

- React、TypeScript、Vite。
- 前端内置 Mock Service 层，所有页面只能通过服务接口读取数据，不直接引用大块全局静态变量。
- Vitest 用于领域逻辑，Playwright 用于三条端到端验收。
- 第一阶段不引入 Redux、复杂微前端、低代码引擎和独立后端服务。
- 真实接口接入时替换 Mock Adapter，不重写页面和领域模型。

### 7.10 关键假设

- 第一版新仓库仍是产品 Demo，而不是直接控制生产靶场的控制平面。
- 9 月 30 日前可以获得一个真实任务、一个可用环境、一个 Agent 和一个数据版本。
- 监管方能够提供最小评分规则和报告样例。
- 数据治理方能够明确至少 P0 至 P3 四级数据处理边界。
- AI 环境生成只使用批准组件，不自动生成或执行未知攻击代码。
- 如果以上假设不成立，930 应缩减为可点击原型和数据契约验证，不用假数据冒充已接通能力。
